# Phase A — Foundation and Migration Safety

## Scope and baseline

Authorised scope: baseline inventory, migration infrastructure, synthetic
preservation fixtures, backup/restore procedures and regression verification.
No Phase B feature work, deployment or provider configuration is authorised.
Baseline: branch `phase-B-community`, commit
`6fe877ccfd06203d0447292833febde414e8d6c6`. The pre-existing specification folder
was untracked and is excluded from the implementation commit.

See [BASELINE.md](BASELINE.md) for SDK, schema, asset and test inventory.

## Database changes

- Room remains version 6. Schema export is enabled. Historical schemas 4 and 5
  were generated by the Room compiler from commits `42ff4b2` and `d8a98fb`;
  schema 6 is generated from the current entities.
- The existing 4→5 and 5→6 migration SQL and destructive fallback are retained.
  Historical version 3 exists in source, but no 3→4 migration or complete
  installed-version inventory has been established. No claim of universal
  historical upgrade support is made.
- PostgreSQL gains an explicit, ordered `0001_current_schema_baseline.sql`
  identical to the existing schema, plus a version/name/checksum ledger managed
  by a separate runner. The ledger was created only in disposable test databases.
- The API's existing startup and `schema.sql` are unchanged. No migration,
  baseline adoption, backup or restore was run against an existing member database.

## PostgreSQL evidence

See [migration procedures](../../server/docs/POSTGRES_MIGRATIONS.md) and
[executed test report](../../server/docs/POSTGRES_MIGRATION_TEST_REPORT.md).

Nine focused scenario groups passed, including read-only status/plan, explicit
baseline adoption with row preservation, repeat/no-op migration, drift rejection,
failed-DDL rollback, and dump/restore content and structure comparisons.
Existing API (19), PostgreSQL contract, community (11), and initialized-database
restart suites passed on isolated test infrastructure. The first restart attempt
against a blank disposable DB failed because the existing test truncates tables
before startup; a separately initialized disposable DB passed the rerun.

No live backend was restarted. Temporary PostgreSQL clusters were stopped and
only their uniquely named synthetic databases were dropped.

## Additional regression checks

The existing relay conversation, classroom signaling-store, proxy configuration,
and test-database safety checks passed. No live Gemini requests or provider
configuration changes were made. The Android unit suite passed 64 tests across 11 suites, with zero failures,
errors or skips; `testDebugUnitTest assembleDebug --offline --no-daemon` succeeded.
The debug APK was assembled, not installed over the main app.

## Room preservation and recovery evidence

See [Room evidence](ROOM_MIGRATIONS.md) and the preserved
[device JUnit results](results/room-migrations.xml). On the Infinix X689C,
Android 11, `connectedValidationAndroidTest` passed all five cases in 5.207
seconds, with zero failures, errors or skips: 4→5, 5→6, 4→6, bundled v5 asset→6,
and closed/checkpointed v6 SQLite backup→separate restored database.
Synthetic users, balances, notes, favorites, messages and pending sync rows were
preserved. All five bundled translation counts were preserved. Separate synthetic
preferences remained unchanged; a SQLite copy is not a complete app backup.
Only the separate validation package was used; the main app's data was untouched.
The tracked bundled database SHA-256 remains identical to baseline.

Disconnected-device and unavailable-emulator attempts did not execute tests;
an exploratory Robolectric dependency download was abandoned and is not counted.

## Documentation integrity

Both testing-spec filenames existed at baseline, have identical content and

## Boundaries and remaining gates

No membership verification, permissions, AI gateway, knowledge management,
attendance, escalation or new AI feature was implemented. No production data,
credentials, provider settings or infrastructure was changed.

The PostgreSQL CLI is limited to explicit confirmed local `_test` database writes
and refuses production mode. Adopting the ledger for an existing app database,
and replacing legacy startup bootstrapping, require a separately reviewed rollout.
Recovery tests prove synthetic database recovery; they do not establish a verified
backup of real member data or media/uploads.

Do not proceed to Phase B automatically. Outstanding installed-version support,
other-device validation and any remaining dependencies must be reviewed alongside the
actual test results. Git commit and final working-tree status are supplied in the
delivery report; this document is included in that commit.

## Acceptance assessment and recommendation

The bounded foundation engineering work and the demonstrated v4/v5/v6 paths
meet the tested Phase A criteria. Universal installed-version migration safety
is not established: versions 1–3 and unknown installations remain unverified,
so destructive fallback remains. No Room version bump or migration SQL change
was necessary. PostgreSQL baseline version 0001 and its ledger were exercised
only in disposable databases, with existing startup behavior preserved.

Local backend validation used Node 26.7 and PostgreSQL 18.6; the Docker template's
Node 24/PostgreSQL 15 combination was not exercised. Full UI/media regression,
real-member recovery, uploads/roles recovery, and production migration adoption
remain outside the evidence. Phase A does not claim deployment readiness.

Recommend owner review of this foundation and explicit authorization before any
Phase B work. No subsequent phase has started.
