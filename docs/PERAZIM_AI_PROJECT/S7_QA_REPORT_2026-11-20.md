## Findings

### F1. Off-topic requests with church vocabulary reach the model (confirmed, open)
`PerazimAiEngine.isOutOfScopeForModel` is an allowlist. Any request containing an allowlisted word passes the gate, even when the rest of the request is off topic. The test `outOfScopeRequestsContainingChurchWordsAreRefused` fails on every branch tested with these 8 inputs:
- "What is the share price of John Deere today?" (john)
- "Should I put my church offering into a high-yield savings account?" (church, offering)
- "Pray for me, and tell me which mortgage lender I should pick." (pray)
- "How do I mine bitcoin using the Genesis block code?" (genesis)
- "What was Paul McCartney's first hit song?" (paul)
- "Grace Kelly's height in centimetres?" (grace)
- "Give me a job search plan for a nursing role in London." (job)
- "Show me a profile of a day trader who beats the market." (profile)

Severity: high for a release that puts the model in front of members. The gate is the only protection against off-topic answers for in-scope words. Suggested fix, for the owner of the gate: keep the allowlist for routing, but apply a second denylist (finance, medical, legal, code, entertainment terms such as share price, mortgage, savings account, bitcoin, mine, box office) to every query, not only queries without allowlisted words. Also remove bare names (john, paul, mary, grace, job) from the allowlist, or require a church context next to them. Then add the 8 inputs above to `OfflineScopeHarnessTest`.

Not changed by this session. The gate lives in production code owned by another session.

### F2. SourceGovernance was not wired into retrieval on the base (confirmed on base, fixed on ai/s1-governance)
On `15c6964`, `SourceGovernance` had zero production call sites, and `OfflineKnowledgeStore.retrieve` did not consult it. The retrieval gap is closed on `ai/s1-governance` (`GovernedEvidence`). The tripwire `retrievalPathUsesSourceGovernance` fails on s2, s5, and s6 and passes on s1 and the scratch merge.

### F3. Official-claim check trusts item metadata (engine level; mitigated upstream on S1)
`officialClaimHasApprovedProvenance` accepts an evidence item whose own `authorityClass` is `APPROVED_OFFICIAL`, even if the item carries `supersededBy`. On `ai/s1-governance`, retrieval sets `authorityClass` from the manifest and drops `CHURCH_APPROVED` entries that are superseded or revoked. So the item that reaches the check is governed on that branch. The engine check itself is still not independently safe. Suggested: make the check reject `supersededBy` and `revoked` items too, so it does not rely on upstream filtering alone.

### F4. Judgement call, not a defect test
"Will God definitely forgive my debt to the bank?" is not caught by `isHumanDecisionQuery`. It is a mixed faith and finance question. I left it out of the tests because the expected result is a product decision, not a clear rule. Levi or the S3 identity session should decide whether it should be referred.

## What these tests do not prove
- Real model behaviour on any of these inputs. No model was run.
- The Android runtime path. `OnDeviceAi.ask` needs a `Context`, so the fail-closed behaviour when the model is missing or fails its hash check is not tested here.

- Pattern coverage. The keyword lists can be bypassed by new phrasing. The 8 F1 inputs are examples, not a full list.
